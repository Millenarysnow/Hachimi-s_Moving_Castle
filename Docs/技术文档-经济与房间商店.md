# 经济与房间商店

本文说明单局金币、商品和背包交易如何保持一致。卡牌身份和建筑来源见 [建筑定义与模型](技术文档-建筑定义与模型.md)。

## 目标与核心方案

**经济保存余额，商店组织交易，定价策略只负责报价。** 三者分离使波次、奖励或界面都能复用同一套收支与交易规则，不需要把逻辑写进 Widget。

**当前完成的是单局商店闭环，不是正式波次经济。** 购买得到卡牌后先入背包，再由棋盘放置；波次结束自动开店、主塔成长上限、正式价格曲线、跨局保存和联网均未接通。

## 结构与依赖边界

- **`UCastleEconomyComponent` 只保存和变更金币。** 它不认识商品和卡牌，任何收入与支出都经过它的校验，避免 UI、奖励和商店各自改余额。
- **`UCastleShopComponent` 显式绑定经济组件、棋盘及棋盘背包。** 初始化只允许一次，防止更换账户后继承上一账户的商品；失效依赖或无效定价配置直接报错。
- **`ICastleCardPricing` 是唯一报价边界。** `UCastleSimpleCardPricing` 是当前测试策略，商店不在策略失败时改用其他算法，否则显示价格与实际扣款会失去共同依据。
- **`ACastlePlayerController` 协调输入，`UCastleShopWidget` 展示结果并转交操作。** 实现在 `Source/Moving_Castle/Castle/Components/`、`Data/`、`Controllers/` 和 `UI/`。

## 商品生命周期

**首次打开免费生成六个商品，关闭后保留商品和售罄状态。** 买完不补货，重新打开不换牌；只有成功刷新才替换整批商品，防止开关界面绕过刷新费用。

**商品只从棋盘的建筑定义池生成一级卡牌。** 当前是等概率、有放回抽样，允许重复；功能牌使用五种颜色和 1～9，路牌固定灰色 0。不能在生成失败时替换为另一类牌，否则实际商品池会偏离配置。

**随机流属于商店初始化后的持续状态。** 生成在临时流上完成，整批卡牌及报价成功后才推进正式流；失败不消耗随机结果，关闭商店也不推进。这样同种子、同配置、同操作序列可复现商品。

**购买价在商品生成时锁定，出售按当次策略报价。** UI 和购买扣款读取同一份商品报价；不能在点击购买时另算一遍，否则策略状态变化可能让玩家支付未展示的价格。

## 交易的一致性

**交易失败必须保留余额、卡牌、商品及随机流的既有状态。** 售罄、无效槽位、满包、余额不足、容量超限和负报价都明确拒绝。零金额允许，负金额、透支和整数溢出由经济组件拒绝。

**购买先校验，再入包并标售罄，最后扣款；出售先验证收益可入账，再移牌入账。** 提交失败会显式恢复已改状态，恢复失败记录错误，不能留下免费卡牌或丢失卡牌。刷新在完整候选商品就绪后替换并扣费，扣费失败恢复原商品。

**金币通知发出时，关联卡牌或商品必须已是该笔交易的提交状态。** 否则观察者会看到“钱已扣、商品未售罄”等中间状态。`bTrading` 阻止金币通知重入第二笔商店交易；扩展监听逻辑不能绕过商店直接改动本笔交易的依赖。

**背包槽数和房间总量是不同约束。** 一张合成卡占一个背包槽，但按其建筑占用格数计入房间总量；场上也按格数计数。把总量改成卡牌数或 Actor 数会使合成凭空释放购买额度。

## 输入与数值边界

**商店开关统一驱动鼠标、移动、视角和建造输入状态。** 输入忽略标志只在开关状态改变时设置；若每次购买通知都叠加设置，关闭商店后玩家仍可能无法移动。商店开启时也禁止巡逻草稿编辑，接入关系见 [NPC 导航接入](Navigation/技术文档-NPC导航接入.md)。

**现有余额、价格和房间上限是测试值，不能解释为正式平衡结论。** 控制器经收入接口发放初始 100 金币；当前策略道路买价 2，功能牌买价为 `5 + 数字 × 2 + (等级 − 1) × 10`，卖价为买价的一半向下取整。刷新费用默认 2、房间总量默认 30；正式数值及主塔成长关系待确认。

## 已否决的方案与扩展准入

- **不在 UI、快捷键或奖励入口复制买卖算法。** 所有入口复用商店与经济组件，否则容量检查、失败状态和价格会随入口不同而分裂。
- **不开关即刷新，不购买后补货，也不加入未设计的保底。** 这些都改变商品生命周期和随机分布，需要先明确玩法规则。
- **新增高等级商品前必须修改容量增量判定。** 当前购买按新增一格检查总量，因为商品只允许一级；只放开等级会低估合成卡的占用。
- **波次开店、免费刷新、权重和锁定需先明确状态归属。** 扩展必须保留报价统一、失败不改变随机流、通知不暴露中间状态及禁止交易重入的约束。
