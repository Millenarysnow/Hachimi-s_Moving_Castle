# 风格化渲染

本文规定游戏画面向《Wanderburg》式低多边形卡通风格转换的方案：表面怎样受光、轮廓线怎样产生、全局光照与调色怎样固定，以及各类既有材质怎样迁入。云海与远景地表的内部设计见[高空云海](技术文档-高空云海.md)和[高空航行地表](技术文档-高空航行地表.md)；建筑模型与材质的组织见[建筑定义与模型](技术文档-建筑定义与模型.md)；卡牌预览见[建筑卡牌表现](技术文档-建筑卡牌表现.md)。参考截图位于 `Docs/参考图/Wanderburg-风格参考-*.jpg`。

## 画面目标

参考图里能稳定辨认、本项目必须复现的特征如下。评审时逐条对照，不以“感觉像”为准。

| 特征 | 参考图表现 | 本方案对应机制 |
| --- | --- | --- |
| 两段明暗 | 受光面平涂；背光面是同一固有色的较暗、略偏冷的一档，中间没有渐变 | Toon BSDF 漫反射色阶 |
| 投影与背光同色 | 树和城堡的投影边缘清楚，暗度与物体背光面一致 | 色阶包含阴影、小光源角 |
| 深色细轮廓 | 城堡、单位、树外轮廓有 1～2 像素深色线，颜色偏暖棕，不是纯黑；内部转折有更淡的线 | 深度+法线描边后处理 |
| 柔和低饱和配色 | 橄榄绿、赭红、木色为主，整体偏暖，对比适中 | 固定曝光、中性色调曲线、全局调色 |
| 无高光、无反射 | 表面全哑光 | 高光色阶清零，关闭反射 |
| 画面干净 | 无景深、无运动模糊、无镜头效果；只有爆炸等特效发光 | 后处理全部关闭，泛光阈值只放过特效 |

本项目与参考的差异必须保留：镜头是自由飞行视角（`ACastleFlightPawn`），会看到天空、云海和三千米下的地表，不是固定俯视。所以风格规则必须在任意俯仰角都成立，不能依赖“地面总在画面下方”。

## 目标与非目标

**目标：** 主塔、建筑（含 PCG 连通件）、主塔气球、空岛实体、空投物、巡逻路点、NPC、敌人与投射物统一为两段明暗加轮廓线的风格；光照、曝光和调色在 `MainMap` 及其内生成的空岛中固定一致；编辑器视口与游戏画面一致，便于后续美术直接按所见调色。

**非目标：** 首版不改云海和地表的着色器，只做调色与曝光复核；不改 UI、卡牌画面和玩法颜色数值；不新做特效、烟雾、粒子美术；不处理 Demo/Test 关卡及未被正式玩法引用的旧资产；不做昼夜和天气变化。

## 核心方案

**引擎原生 Substrate Toon BSDF 负责表面明暗，全屏后处理材质负责轮廓线，关卡里的一个无界后处理体积负责曝光与调色。**

选择原生 Toon BSDF 的原因：项目已开启 Substrate（`r.Substrate=True`，`r.Substrate.ProjectGBufferFormat=0` 即 Blendable GBuffer），UE 5.8 发行版自带实验性的 `UMaterialExpressionSubstrateToonBSDF` 与 `UToonProfile`（`Engine/Source/Runtime/Engine/Classes/Engine/ToonProfile.h`，着色器 `Shaders/Private/Substrate/SubstrateToonBSDF.ush`）。它在逐灯光计算时就把明暗量化成色阶，能和虚拟阴影贴图、天光与点光正确叠加，也能按材质选择配置。已核对源码：Toon 在 Blendable GBuffer 下可以存储，只是不能使用各向异性。

轮廓线放在后处理：建筑由大量独立 `UStaticMeshComponent` 组成，NPC 与敌人走 Mass 骨骼实例批次，只有屏幕空间方案能用一份代价覆盖全部对象。

## 结构与依赖边界

- **资产归 `/Game/MovingCastle/Rendering/`。** 下设 Toon 配置、表面材质函数、母材质和后处理材质。建筑、单位和空岛只引用这里的资产，本目录不引用任何玩法资产。
- **生成工具归 `Source/Tools/Stylized/`。** 沿用 `Source/Tools/CardFace` 的做法：描边 HLSL 作为独立文件保存，由 Python 脚本建成材质；材质迁移也由可重复运行的脚本完成。节点图由工具完整拥有，不在编辑器里手工连线后再与脚本分叉。
- **C++ 只承担两件事：** 替换代码里硬编码的 `BasicShapeMaterial` 引用，以及给少量信息面写 Custom Stencil。资产路径与 Stencil 值集中在 `Source/Moving_Castle/Castle/Rendering/` 的一个头文件中，各构造函数引用它，不各自写路径。
- **光照与调色归关卡。** `MainMap` 持有太阳、天光、雾和风格化后处理体积。空岛生成在同一关卡里，自动继承这些设置，不另设一套。
- **红线：玩法代码不读、不写任何渲染风格参数。** 违反后，换材质或调参就会牵动玩法逻辑与自动化测试。
- **红线：不修改第三方包和模板资产**（`RPGMonsterWave2PBR`、`Characters/Mannequins`、`InterchangeAssets`、`StylizedWeather` 的材质）。需要 Toon 版本时，在本目录新建项目自有的母材质，再让项目侧的材质实例或覆盖槽指向它。修改包内资产会在更新素材包时被静默覆盖。

## 光照与全局设置

**全局光照与反射在项目级关闭**（`r.DynamicGlobalIlluminationMethod=0`、`r.ReflectionMethod=0`），环境光只来自天光，再用小半径 SSAO 补接触暗部。原因有三：一、参考画面的暗部是均匀平色，Lumen 的反弹与天空遮蔽会让暗部随环境起伏；二、玩法要求玩家看清封闭房间里走动的 NPC，Lumen 会把有天花板的房间压暗；三、建筑飞入和合并动画频繁移动零件，Lumen 的屏幕追踪在这些地方会有噪点和延迟。设在项目级而不是只设在后处理体积里，是为了编辑器视口和所有入口看到同一结果。**不要为了“室内太亮/太平”重新打开 Lumen**，平涂的室内正是想要的效果。

**太阳方向固定，不随时间变化。** 色阶和调色都是按一个固定的入射方向标定的，昼夜变化会让受光面和背光面的比例不断变化。初始高度角取 45°～55°：低于这个角度，45 m 以上的主塔投影会盖住大半座城堡；高于这个角度，侧墙会全部落进背光档，画面会发平。方位按 `PlayerStart` 初始朝向放在镜头左后上方，使默认视角下能同时看到受光面和背光面。

**投影边缘要清楚。** 保留虚拟阴影贴图；太阳的光源角从当前的 0.5357 降到 0.1 左右。关闭接触阴影，因为它会在平涂面上产生细碎的暗斑。

**天光提供带色温的平坦环境光。** 当前天光使用指定立方体贴图、强度 1.5、偏蓝色调，并开启“下半球为黑”。改为下半球使用暗暖灰：城堡悬空，玩家会从下方看到建筑底面，纯黑底面在风格里是破洞。天光颜色决定暗部的冷暖倾向，这是调整阴影色的第一个手段。

**光照由 `BP_StylizedWeather_fix` 持有时，只能通过它已有的配置固定成静态预设。** 若它每帧推进时间、无法配置为静态，就改由关卡直接摆放原生太阳、天光和雾 Actor，并移除这个蓝图对光照的控制。不允许在该蓝图里加逻辑来“锁时间”，这违反项目“逻辑不进蓝图”的约定。

## 表面着色：Toon 配置与材质函数

**只用三份 Toon 配置，每个材质必须属于其中之一：**

| 配置 | 用途 | 区别 |
| --- | --- | --- |
| `TP_Surface` | 建筑、连通件、空岛、道具、路点 | 标准两档，高光为零 |
| `TP_Unit` | NPC、敌人、投射物 | 背光档更亮，保证单位站在城堡阴影里时仍能辨认 |
| `TP_Metal` | 黄铜、青铜、铜等金属件 | 在两档之上加一条硬边高光，区分金属与木石 |

配置数量刻意控制得很少：配置决定全局观感，逐材质新建配置会让同类表面明暗不一致，也会让后续调色变成逐个修改。新增配置的前提是出现一类现有三份都无法表达的表面。

**色阶的输入是半 Lambert 乘阴影，不是 NoL。** 源码中漫反射色阶的输入为 `(NoL × 0.5 + 0.5)`；开启 `bDiffuseRampIncludeShadow` 后，这个值再乘以阴影透射率。因此色阶横轴 0.5 才是明暗交界，处于投影中的像素输入接近 0。三份配置都开启 `bDiffuseRampIncludeShadow`，让投影和背光落在同一档，这正是参考图中“投影与背光同色”的来源。色阶从约 0.55（NoL≈0.1）处跳变，过渡宽度约 0.02：宽度为零时，低多边形的斜面会出现锯齿闪烁；过宽则会重新出现渐变。

**背光档写成带色相的颜色，而不是一个灰度值。** `DiffuseRamp` 是线性颜色曲线，背光档取略偏冷的颜色（初值约 0.45/0.47/0.58，再结合天光调整）。暗部偏冷、受光面偏暖，是参考图柔和感的主要来源。

**高光默认为零，间接光比例保持 1。** `TP_Surface` 与 `TP_Unit` 的高光色阶全段为 0，并关闭反射，画面完全哑光。`r.Substrate.Experimental.ToonUnifiedDiffuse` 与 `ToonReflectionQuantizationEnabled` 保持默认关闭：前者只在多盏灯同时照亮一个面时才有意义，后者依赖已关闭的反射，而且两者都是只读 CVar，开启会触发全量着色器重编译。

**Toon BSDF 只出现在三个材质函数里**：`MF_ToonSurface_Surface`、`MF_ToonSurface_Unit`、`MF_ToonSurface_Metal`。每个函数内含一个已绑定对应配置的 Toon BSDF 节点，输入为固有色、自发光与可选法线，输出 Substrate 材质。各母材质和迁移后的材质都通过这三个函数接到 Front Material，不直接放 Toon 节点。这样做是因为该功能处于实验阶段：引擎升级导致接口变化，或者必须更换实现时，只需修改三个函数。

## 材质迁移

已经从 `MainMap` 和正式玩法资产递归统计过引用的材质，按族处理。迁移脚本对每个材质必须明确归类；遇到未列入映射表的材质、参数或配置时，报出资产路径并停止，不归入任何默认类别。

**HachimisV4 主体材质（约 148 个，含盾塔分组）原地改写。** 这些是独立的 `UMaterial`，固有色写在材质输入的常量中，没有节点。因此 `MaterialEditingLibrary` 统计到 0 个节点，`get_material_property_input_node` 也取不到颜色。颜色必须从材质自身的编辑器数据中读出（参考 `HachimisV4BindCommandlet`，用编辑器 C++ 读取 `UMaterialEditorOnlyData` 的 BaseColor 常量），再写成同名材质里的 `BaseColor` 向量参数并接入对应的材质函数。金属与非金属按名字建显式映射表。**必须原地改写，不能新建材质实例再整体替换引用：** 装配记录与目录保存正式网格及材质路径，`BuildPlan` 判断零件能否原地保留时也会比较材质身份；更换资产路径会让合并动画误判，删除后重建同名资产还会留下内存中的悬空引用。

**Interchange 导入的材质实例（约 220 个，母材质为 `FBXLegacyPhongSurfaceMaterial`）改挂父材质。** 这些实例分布在主塔 `PrototypeUpgrade/MainTower`、`SupportTowers`、`SupportProps` 和 `DaoDun`。最后一组仍被 `BP_Variant_LV1/LV2` 用作导航模板，护栏、楼板和梯子都可见。新建 `M_Toon_FBXPhong`，暴露与原母材质同名的参数，再把这些实例的父材质改为它，资产路径和身份保持不变。改挂前先统计全部实例实际覆盖的参数；新母材质必须支持全部这些参数，有任何一项不支持就列出来停止，不允许让参数在改挂后静默失效。

**单位材质改用项目自有母材质。** `M_MassEnemyTint` 本就归项目所有，原地改接 `MF_ToonSurface_Unit`，保留参数名与自发光，它的 6 个实例（含炮弹）随之生效。`RPGMonsterWave2PBR` 的 Polyart 材质要在本目录复刻其遮罩染色逻辑，作为 Toon 母材质，再建项目侧实例并写进敌人的可视化覆盖。NPC 的 `SKM_MassHumanoid` 两个槽也走同样的覆盖。覆盖必须写进原生骨骼批次描述 `UCastleMassHumanoidVisualizationTrait::MaterialOverrides`，见[Mass单位框架](Mass/技术文档-Mass单位框架.md)。新母材质必须勾选骨骼网格及实例化骨骼网格的用途标记，否则 Mass 批次会显示引擎默认的网格材质。

**C++ 里的 `BasicShapeMaterial` 按语义分成两类。** 空岛主体、主塔气球、地面格等世界几何改用 `M_Toon_BasicColor`（`TP_Surface`）。塔侧格面、网格光标等信息面改用不受光的 `M_Info_UnlitColor`。两者都保留参数名 `Color`，现有动态材质实例的设色调用不需要改。色号是规则信息，信息面使用不受光的材质以便在背光面与投影中辨识红、黄、蓝、绿。具体调用点包括 `CastleTowerSideGridComponent`、`CastleGridCursor`、`CastleGroundTileActor`、`CastleMainTowerBalloonComponent`、`CastleBuildingBase` 以及四个空岛类，逐个按语义归类。材质加载失败时，用 `UE_LOG` Error 报出类名与路径，不退回引擎材质。

**保持原样的材质：** 护盾球与次数文字、敌人激光、巡逻虚线、路点圆圈、支援飞行等不受光或半透明的指示物；`StylizedWeather` 天空与太阳；云海与地表；全部 UI 和卡面材质。巡逻路点的 4 个实体材质属于世界物件，迁到 `TP_Surface`。

## 轮廓线后处理

**一个后处理材质，用深度和法线的不连续生成轮廓。** 在中心像素与上下左右四个邻点之间比较。深度差按中心深度做相对比较，并随视线与表面法线的夹角放宽阈值，否则塔墙这类大平面在掠射角下会整片误判成边。法线夹角超过阈值产生内部线，强度约为外轮廓的一半：参考图里城堡内部的结构线明显比外轮廓淡，HachimisV4 是硬边低模，全强度的内部线会让画面发脏。只有较近的一侧画线，线条才落在前景物体上，不会在背景上加倍。

**轮廓颜色由当前像素压暗再偏暖得到，不使用固定黑色。** 这样木头上的线发棕、草绿上的线发墨绿，与参考图一致。线宽按 1080p 下约 1.5 像素随分辨率缩放，避免高分辨率下线条变细、失去存在感。

**描边在时间超分之前执行**（混合位置 Scene Color Before DOF）。这一步在渲染分辨率上读取带抖动的深度，再由 TSR 一并抗锯齿，线条稳定。放在色调映射附近（TSR 之后）会读到与输出分辨率不对应的深度，线条会闪烁和锯齿。半透明物体不写深度，自然没有轮廓；护盾球后面的轮廓透过球体可见，这符合预期。

**距离淡出是不描边背景的唯一依据。** 轮廓线从约 150 m 开始减弱，到约 400 m 完全消失，三千米下的地表和天空自然不画线。体积云不写深度，也不会被描边。主塔对着天空的剪影仍然有线。不要另加“按 Actor 类型排除”的规则。

**需要单独排除的不透明物体用 Custom Stencil 标记。** 预留一个 Stencil 位表示“不描边”，只由 C++ 写到少数确实需要的信息面组件上，比如格面上的数字（数字的实现方式由实现者核实后决定是否需要）。使用前需要把项目的 `r.CustomDepth` 设为带 Stencil 的模式。Mass 单位不能也不需要写 Stencil。

## 曝光与调色

后处理体积放在 `MainMap`，设为无界：

- **固定曝光，关闭自动曝光与局部曝光。** 自由镜头在看向明亮云海和看向城堡之间来回切换，自动曝光会让城堡忽明忽暗，调色标定随之失效。项目默认的局部曝光对比度为 0.8，在体积里要设回中性值。
- **色调曲线设为中性**（Film 的 Tone Curve Amount 取 0；若 5.8 字段名不同，以引擎为准）。目标是“所见即所调”：固有色为 X 的表面在受光档的显示值约等于 X。按这个目标，用一块中灰标定板一次性定下曝光补偿。默认的电影色调曲线会压暗、压饱和平涂色，美术调出的颜色与屏幕结果就对不上。
- **全局调色只做轻度处理。** 饱和度约 0.85～0.9，色温略暖，加轻微暗角。参考图的低饱和主要来自固有色本身。全局降饱和过多会让四种玩法色难以区分。
- **关闭景深、运动模糊、色差、胶片颗粒和镜头光晕。** 泛光阈值设到只有特效的自发光能超过。

## 背景层

**云海和地表首版不改着色器。** 改为固定曝光后，它们的亮度会发生变化。复核时只调太阳强度、曝光补偿和天光，使云顶不过曝、透过薄云仍能看清地貌。不修改 `M_AerialCloudscape` 或 `M_AerialTerrainSurface`，因为它们的不变量由各自的技术文档约束。如果复核后确实需要改它们，按对应文档另行设计。

## 反直觉的坑

- **Toon BSDF 是实验功能，接口可能随引擎升级变化。** 所以它只能出现在三个材质函数里。任何地方直接放置 Toon 节点，都会让日后的迁移面扩散到上百个资产。
- **只开启 Toon 而不关闭自动曝光和色调曲线，看起来会“不像卡通”。** 根因在后处理链，不在材质。排查顺序是：曝光，色调曲线，再看色阶。
- **V4 材质节点数为 0 不等于没有颜色。** 颜色在材质输入常量里，见上文。
- **卡牌预览与场上建筑共用网格和材质。** 迁移后必须确认 `UCastleBuildingPreviewSubsystem` 的法线捕获仍然正确，且场景后处理体积不进入捕获。捕获使用自己的 ShowFlags，不能为了预览去改世界后处理。
- **新母材质缺用途标记时，运行时会显示默认网格材质，而不是报错中断。** 迁移完成后必须进游戏检查 NPC、敌人和飞入零件。
- **着色器编译量大。** 首次迁移会编译数百个材质，属正常耗时，不要因此合并或删除材质来“减少编译”。

## 被否决的方案

- **后处理量化光照**（用 SceneColor 除以 BaseColor 估算光照，再分档）：雾、自发光和天光会混入估算值；阴影颜色无法按材质控制；Substrate 下读取 GBuffer 也不可靠。只有在原生 Toon 无法使用时才可能重新考虑，并且必须先征得用户同意。
- **Unlit 加材质内自算光照：** 拿不到虚拟阴影贴图投影，丢失“投影与背光同色”这一核心特征。
- **自定义着色模型：** 需要源码版引擎，项目使用的是发行版。
- **反向外壳描边：** 建筑的独立组件和 Mass 单位都要多画一遍；V4 的硬边法线会让外壳开裂。
- **按物体 ID 或 Stencil 描剪影：** 要求所有组件与 Mass 批次写自定义深度，成本高，并且新增对象容易漏标。
- **保留 Lumen：** 理由见“光照与全局设置”。
- **用材质实例整体替换 V4 材质：** 会改变资产路径与材质身份，理由见“材质迁移”。
- **后处理分档做卡通云：** 透过薄云看到的地表会一起出现色带，而且这会破坏云海文档的“近透远密”约束。

## 分期与准入

每期独立提交，以固定机位截图（默认视角、俯视、斜视城堡、空岛内、看向云海）与参考图对照评审。

1. **验证期：** 一座 V4 建筑、一个 NPC 和一种敌人接入 Toon 函数。必须确认在 DX12 SM6 下能编译，虚拟阴影贴图正确进入色阶，Mass 实例化骨骼网格能正常显示，卡牌预览不受影响。任何一项不成立都立即停止，向用户报告，不自行改用被否决的方案。
2. **全局光照与调色：** 关闭 Lumen，固定太阳与天光，加入后处理体积，完成中灰标定。
3. **材质迁移：** 按上文各族逐一完成，迁移脚本可以重复运行，结果保持一致。
4. **轮廓线：** 在后处理材质和描边参数确定后，加入 Stencil 排除。
5. **整体调色与背景复核。**

## 未实现的部分与扩展准入

- **卡通化云海与地表：** 必须先在各自技术文档中定义新的表现边界，并保持航程与近透远密等不变量。
- **玩法色板统一**（格面、卡牌与建筑配色向参考的低饱和色板靠拢）：牵涉规则辨识度与 UI，需要用户另行确认色值。
- **特效与烟雾的卡通化**（参考图里实心的白色烟团和硬边爆炸）：属于特效美术，可以复用 `TP_Surface` 与轮廓线，不改变本文架构。
- **昼夜或天气：** 必须为每个时段分别标定曝光与色阶，不能让太阳自由旋转。
