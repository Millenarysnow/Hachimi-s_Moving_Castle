# 技术文档 - NPC 导航

本文写给接手 NPC 寻路的 agent，说明这套方案的思路，以及哪些问题已经有结论、不必重新讨论。关卡配置、操作和验收见 [NPC 共享导航](NPC共享导航.md)，字段和参数以源码为准。

## 要解决的问题

NPC 由 Mass 驱动，数量可能很多。玩家放置 1～N 个路径点，所有 NPC 按 1→2→…→N→1 循环巡逻，相邻两点之间走 NavMesh 最短路。NavMesh 使用 UE 自带的 Recast，城堡建筑会在运行时建造、飞入和合并，可走区域随之改变。

难点是让寻路成本与 NPC 数量无关。整体思路是：**路线只算一份，所有 NPC 共享；每个 NPC 只记录自己走到了哪里。**

## 整体结构

系统分三层，每层只做自己的事：

1. **路径点输入**：`ACastlePatrolRoute` 管理玩家的草稿点，按 Enter 时把整组点提交给导航子系统。它自己不寻路。
2. **集中求解与发布**：`UCastleNavigationSubsystem`（每个 Game/PIE 世界一个）持有唯一的路线请求，决定 NavMesh 何时更新，求解整条闭环，并发布只读快照。
3. **Mass 跟随**：`UCastleMassPatrolProcessor` 每帧取一次快照，按 Chunk 并行推进所有 NPC 的进度。`ACastleMassSpawner` 沿路线生成 NPC 并写入初始进度。

代码在 `Source/Moving_Castle/Units/Navigation/` 及其 `Interaction/`、`Mass/` 子目录，生成器和单位命令在 `Units/Mass/`。

## 路线计算

- **一次算完整条闭环。** 提交 N 个点后，集中求解 1→2、…、N→1 共 N 段，全部成功才发布。“NPC 到点后再算下一段”的做法已经否决：它让计算量随 NPC 数和圈数增长，也无法提前发现后面的路段不可达。现在 NPC 到点、转弯、绕圈都不触发寻路，只有路径点变化或 NavMesh 更新才会重算。
- **顺序由玩家决定**，不做重排。每段取默认过滤器下的最小代价路径。默认 NavArea 代价相同，所以等同最短距离；以后加入有代价的 NavArea，“最短”的含义会随之改变。
- **整条成功或整条失败。** 任一点投影不到 NavMesh、任一段不可达或只有部分路径、相邻点重合、路线经过 NavLink，都会让整条路线作废：发布空快照，写入 `LastFailure`，NPC 停下。不发布已算好的前几段，也不用直线兜底。
- **NavLink 暂不支持。** 跳跃、门、传送还没有对应动作，遇到就拒绝整条路线，不能当普通路段直线穿过。
- **单个点表示原地待命**，不发起查询。空点列不能提交，要清空路线用 `ClearSharedRoute`，NPC 随即停止。
- 玩家编辑的是草稿，放点和撤回都不寻路，原路线照常运行。提交相同点列会复用已有请求。

## 共享快照

- 快照里有三种点，不能混用：投影后的玩家路径点（`Waypoints`）、UE 求出的转折点（`Points`）、沿 NavMesh 走廊等距采样的表面点（`PatrolPoints`，默认间距 20 cm）。NPC 只沿表面采样点移动。
- 表面采样在求解时一次完成，所以楼梯高度只算一份，NPC 运行时不再投影地面或做射线检测。采样只取该段路径走廊内的多边形，并优先选高度连续的点，避免吸到上下重叠的另一层楼板。
- 快照不可变。重算时发布新对象，旧对象不修改。快照不保存 NavMesh 多边形引用，因为 Tile 重建后这些引用会失效。
- 求解和发布只在游戏线程进行。Mass 工作线程只读快照和实体 Fragment，不访问 UObject。
- 三个版本号各有用途：`NavigationRevision` 表示 NavMesh 完成一次构建，`RouteRevision` 表示玩家点列变了，`PathRevision` 每次发布（包括失效）都递增。NPC 通过 `RouteRevision` 是否变化，区分“同一路线因 NavMesh 更新而重算”和“玩家换了路线”。
- `RequestSharedPatrolRoute` 返回 true 只表示请求已接收，NavMesh 可能还在构建。使用前必须确认快照 `bValid && bClosedLoop`。
- 旧的单段接口 `RequestSharedPath` 和巡逻共用同一个请求槽，调用它会替换巡逻路线，不能拿来维护第二条路线。

## NavMesh 更新时序

固定顺序是：几何开始变化 → 立即发布失效快照，NPC 停下 → 所有变化结束 → 下一帧解锁并全局重建 NavMesh → 等构建彻底完成 → 重算整条闭环并发布。

- 动画期间用导航构建锁压住生成。变化靠开始/结束配对计数：棋盘的同步放置、替换、删除用 `FScopedCastleNavigationChange`；飞入和合并组件在起播时调用 `ObserveAssembly` / `ObserveMerge`，由组件的完成通知结束。同一来源可以嵌套，多座建筑可以并发。
- 最后一项变化结束后至少等一帧才提交。原因是飞入完成的回调可能同步触发自动合并，立即提交会把一次业务变化拆成两轮构建，产生一条中间路线。
- 每轮只调用一次全局 `RebuildAll`，不依赖动画期间累积的脏区，也不按零件归位次数重建。局部 Tile 调度目前没有做。
- 脏区队列、导航 dirty 标记和异步构建全部结束才算稳定。构建期间又开始变化，就取消这次构建，并入下一轮，防止过时结果覆盖新状态。构建超过 60 秒按失败报错。
- 整套调度由事件驱动。稳定后子系统不 Tick，也不扫描建筑。以后新增任何改变通路的玩法，都必须接入这套开始/结束配对，取消和销毁也要发出结束，否则锁不会释放。只靠引擎自动标记脏区，共享路线不会失效。

## Mass 跟随

- 每个 NPC 的 `FCastleMassPatrolFragment` 只存：是否巡逻、是否受阻、上次见到的版本号、当前玩家路段、累计距离、速度、圈数。NPC 不存路径，也没有 AIController 或寻路任务。
- 位置由累计距离在采样点上二分查找得出，一帧跨过多个转折甚至整圈也不会离开折线。转向插值只改朝向，不改轨迹，以免拐角处切进墙里。速度写回 Velocity，驱动现有的 Mass 动画。
- **巡逻进度不能用最近点反推。** 去程和返程可能共用同一段楼梯，同一位置对应不同阶段。这个问题已经出现并修正过：生成器沿路线均匀生成时，直接写入每个 NPC 的精确距离和路段。
- 收到新快照时重新绑定：`RouteRevision` 没变（只是 NavMesh 重算）就只在原玩家路段内找最近点；`RouteRevision` 变了才在整条新路线上找。离路线超过 50 cm 的 NPC 标为受阻并停下，汇总报一次警告。不传送，不单独寻路，也不每帧重试，等下一份快照或重新加入。
- 路线失效期间 NPC 保留巡逻状态，新快照到达后自动继续。`MoveUnitsTo`、`SetUnitsVelocity`、`StopUnits` 会关闭该单位的巡逻；普通移动 Processor 跳过巡逻中的单位。同一个单位任何时刻只由一个系统负责位移。
- 已存在的单位可以调用 `FollowSharedPatrolRoute` 加入，同样受 50 cm 限制。从任意位置寻路接入路线还没有实现。

## 导航输入

- 不另建建筑连通图或第二套路网，NavMesh 直接来自建筑最终的实际碰撞。
- 建筑基类 `ABuildingNavigationActor` 只允许 Building Gameplay Root 分支下的组件参与导航。美术组件即使勾选了影响导航也会被排除；功能组件仍要自己配好碰撞。
- 棋盘地块只用于 Visibility 射线交互，不提供行走面。因此能放下路径点不代表那里有 NavMesh，投影失败时会报错。
- Recast 必须使用 Dynamic 运行时生成，否则请求直接报错。水平体素为 5 cm，是为了保留 100×100 cm 功能楼板的顶面；Agent 使用默认的一种，半径 35 cm。

## 未实现的部分与扩展底线

尚未实现：从任意位置接入路线、单位避让与编队、路径点停留、多条路线、多种 Agent、存档、网络同步、NavLink 动作。

扩展时守住以下几点：

- 不能退回到每个 NPC 各自计算巡逻路线。局部避让可以加，但不能带回这部分成本。
- 新情况先定义行为再实现，不能靠放宽失败检查或加静默回退来“支持”。
- 如果把求解改成异步，结果必须按请求和导航版本校验，过时的直接丢弃。

验证时最直接的信号是 `PathQueryCount`：路线就绪后 NPC 持续绕圈，它不应增长；N 个点的一次完整求解只增加 N。具体测试和演示关卡见配套说明。

修改设计时同步更新本文对应的结论和理由。字段、参数、命令和测试明细留在源码和配套说明里，本文保持能快速通读的长度。
