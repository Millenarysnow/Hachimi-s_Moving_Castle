# 技术文档 - NPC 导航

本文记录已经确定的设计结论及理由，供没有会话上下文的 agent 接手。维护时保留这个粒度；接口、参数和操作细节按需查源码及[配置与验收说明](NPC共享导航.md)，避免将本文扩写成实现清单。

## 已确定的总体方案

玩家放置有序路径点，所有 Mass NPC 共用一条 **1→2→…→N→1 的完整循环路线**。NPC 数量只影响跟随计算，不影响寻路次数。

以下结论是继续开发的前提：

- **先算完整条路线，再让 NPC 使用。** N≥2 时，一次集中求解全部相邻路段及 N→1，成功批次共执行 N 次原生查询；到点、转弯、绕圈都不触发寻路。
- **玩家给出的顺序固定。** 各相邻点之间使用 UE NavMesh 最小代价路径。默认区域代价相同时按距离选路；以后增加 NavArea 代价时，应明确这会改变“最短”的含义。
- **整条路线共同成功或失败。** 任一段不可达、投影失败或需要尚未支持的特殊动作，整条新路线无效，给出原因并暂停 NPC。不能用半条路线、部分路径或直线穿障碍代替。
- **导航沿用 UE 的 Recast NavMesh。** 建筑实际功能碰撞是导航输入，不再建立建筑六面连通图或另一套路网。
- **寻路和移动逻辑使用 C++ 与 Mass。** NPC 只保存自身进度，不各自持有路径、AIController 或寻路任务；蓝图和关卡负责配置。

当前每个 Game/PIE 世界只有一条共享路线，使用默认导航 Agent。单个路径点表示原地待命，清空路线表示暂停巡逻。

## 整条路线怎样交给 NPC

玩家编辑的是草稿，只有提交时才替换共享请求；连续放点和撤回草稿不寻路，已发布的路线可以继续工作。相同请求复用结果，实际需要重算时由路径点变更或导航刷新触发。

集中求解除了生成绕障碍的转折，还会沿选中的 NavMesh 走廊预采样表面高度和累计距离。**这份贴楼梯的采样也由所有 NPC 共享**，无需每个 NPC 每帧再投影或查询地面。玩家路径点、求解器转折点和表面采样是三种数据，不能混用。采样近似 NavMesh 表面，不承担精确的物理脚底碰撞。

结果以不可变快照发布，Mass 每轮获取一次，供整批实体使用。重算时构造新快照，旧数据不原地修改，也不长期保留会随 Tile 重建失效的多边形引用。工作线程只读取快照和实体数据；集中寻路与发布在游戏线程完成。

快照将三个变化分开标识：`NavigationRevision` 表示网格更新，`RouteRevision` 表示玩家路线变化，`PathRevision` 表示一次结果发布（包括失效）。这样才能区分“原路线因建筑变化重算”和“玩家换了路线”，决定怎样保留 NPC 的行走阶段。

接入时有两个容易误解的约定：请求返回成功只表示**已接收**，消费前仍要确认结果是有效闭环；持有旧快照也不代表旧路线仍可通行。旧开放路径调试接口与巡逻共用一个请求槽位，会替换巡逻请求，不能拿来并行管理另一条路线。

## 建筑变化后何时重算

已经确定的时序是：**几何开始变化 → 路线失效并暂停 NPC → 整轮变化结束 → 更新 NavMesh → 重新算完整闭环 → NPC 恢复跟随。**

这里有三项不能丢失的设计：

1. 建造、飞入和合并通过开始/结束通知配对，由导航子系统统一持有构建锁。多座建筑可以并发，同一来源也可以嵌套；不逐帧扫描建筑，不按零件归位次数重建。
2. 最后一项变化结束后，至少到下一帧才提交。飞入完成的回调可能立即触发自动合并，立即解锁会把一次业务变化拆成两轮，产生中间结果和重复计算。
3. 等引擎脏区和异步构建任务确实结束，才允许发布新路线。构建期间又有变化，就取消旧构建并入下一轮；不能发布过时结果。

当前每轮采用全局 NavMesh 重建，稳定后导航子系统停止 Tick。新增会改变通路的业务必须接入这套通知；仅让引擎自行标记脏区，不能保证共享路线及时失效。开始通知还必须覆盖取消和销毁时的结束配对，否则可能一直锁住更新。

建筑导航资格统一限定在 **Building Gameplay Root 类型组件及其后代**，分支外美术不参与。功能组件仍须自行配置正确碰撞和导航开关。棋盘显示地块只用于 Visibility 射线交互，始终不提供单位行走面；能瞄准放点不代表该处有可走 NavMesh。

## NPC 怎样移动并保留进度

每个 NPC 保存自己的距离、当前玩家路段、速度和圈数，位置按共享路线的累计距离采样。这样即使一帧跨过多个转折或整圈，也能保持在路线折线上。转向平滑只改变朝向，不改变行走轨迹，避免切角穿墙；速度继续驱动已有 Mass 骨骼实例动画。

推荐沿已算好的完整路线均匀生成 NPC。生成时直接写入已知的距离和路段，**不能重新用空间最近点反推进度**：去程和返程可能共用同一段楼梯，最近位置相同，巡逻阶段却不同。这是已经遇到并修正过的问题。

路线更新后的处理也已明确：

- 同一组玩家路径点因 NavMesh 更新而重算时，只在 NPC 原路段内重新定位，保留去返阶段；玩家改变点列时，才允许在整条新路线中定位。
- 只允许附近重绑，当前三维距离阈值为 50 cm。超过阈值的单位停止并提示，不自动传送或另发接入寻路。阻塞单位不会每帧重试，需要新结果或显式重新加入。

路线暂时失效时保留巡逻意图，等新结果恢复；显式调用直达移动、设速度或停止命令则解除该单位巡逻。普通移动 Processor 会跳过仍处于巡逻模式的单位，保证同一单位只有一套系统负责位移。

## 当前边界与后续扩展

当前方案服务于共享中心线上的循环行走。任意出生点接入、单位避让/编队、逐点驻留、多条路线、多种 Agent、存档和网络同步尚未实现；NavLink 跳跃、门和传送等连接当前明确拒绝。增加这些能力时应先定义行为，不能靠放宽失败检查或增加静默回退实现。

扩展必须保留“集中计算、完整发布、各自保存进度”的基础。以后若将整条路线计算异步化，还需按请求和导航版本丢弃过时结果；若增加局部避让，也不能重新引入每个 NPC 重算整条巡逻路线的成本。

## 接手入口

日常只需从对应职责进入源码：

- [CastleNavigationSubsystem](../../Source/Moving_Castle/Units/Navigation/CastleNavigationSubsystem.cpp)：集中求解、共享快照和 NavMesh 更新调度。
- [CastleMassPatrolProcessor](../../Source/Moving_Castle/Units/Navigation/Mass/CastleMassPatrolProcessor.cpp)：独立进度、重绑和批量跟随。
- [CastleMassSpawner](../../Source/Moving_Castle/Units/Mass/CastleMassSpawner.cpp)：沿路线生成并初始化精确进度。
- [CastlePatrolRoute](../../Source/Moving_Castle/Units/Navigation/Interaction/CastlePatrolRoute.cpp)：玩家草稿与整组提交。外部单位命令见 [CastleMassUnitSubsystem](../../Source/Moving_Castle/Units/Mass/CastleMassUnitSubsystem.cpp)。

可直接运行 `/Game/MovingCastle/Maps/L_MassPatrolDemo`：32 个 NPC 共用四段路线，初次就绪后 `Path queries=4`，持续绕圈不应增加。自动化重点是 `MovingCastle.Patrol.SharedLoop`（完整路线与 1024 实体进度）和 `MovingCastle.PatrolDemo.Runtime`（实际显示与输入）；涉及建造刷新时再回归原导航测试。
