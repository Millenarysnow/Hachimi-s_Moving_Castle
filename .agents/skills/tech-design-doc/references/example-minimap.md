# 技术方案 · RTS 小地图

## 1. 目标与非目标

### 1.1 目标

首版要提供经典 RTS 小地图的完整基础闭环：

- 持续显示会漂移、倾斜、翻覆和被实时雕改的冰山地形；
- 每帧显示存活单位、存活建筑与当前主相机可视范围；
- 左键点击或拖动小地图时移动主相机观察焦点；
- 地形和标记刷新率允许跟随游戏帧率，不以低频刷新掩盖性能问题；
- gameplay 完全不知道小地图存在，且不修改任何 gameplay 代码；
- 单位换模型、换动画、换表现后端或增加内部逻辑时，小地图无需兼容这些实现细节；冰山几何从方格变成多边形、六边形或其他表现网格时，小地图仍从最终可渲染结果得到轮廓。

### 1.2 非目标

首版不做战争迷雾、雷达侦测、隐身/潜水显隐规则、缩略图烘焙、旋转地图、缩放/平移地图本身、单位朝向箭头、攻击提示动画、导航可达性着色，也不为小地图建立第二份地形数据。

这些能力以后可以在 UI 侧继续叠加，但不能以破坏本文依赖红线为代价。

## 2. 核心方案：真实地形捕获 + UI 批量标记

小地图采用混合架构，而不是让一台 SceneCapture 摄像机重画整个世界：

```text
冰山注册表 ──> UI facade ──> ShowOnly 地形集合 ──> 正交 SceneCapture ──> RenderTarget
战斗只读快照 ─> UI facade ──> 纯 UI 标记帧 ───────> Slate/UMG 单次批绘
主相机视图 ───> UI facade ──> 视野四边形 ─────────> Slate/UMG 单次批绘
小地图输入 ───> UI facade ──> 既有 CameraPawn 公开入口
```

SceneCapture 只承担它最擅长、也最难由数据低成本复刻的部分：**最终冰山表面**。单位、建筑、相机框等高频且数量可能很大的对象不捕获真实模型，而由 UI 从既有只读快照批绘为简单图元。

这一拆分同时满足准确性和成本边界：

- 地形实时雕改后，捕获的是现成的最终表现网格，不需要 UI 理解体素、chunk、Surface Nets 或未来六边形数据结构；
- 单位不重复提交骨骼网格、材质、动画与阴影，模型复杂度不会传导到小地图成本；
- 每个单位不创建一个 UWidget，标记数量增长时主要成本是一次连续数组遍历和少量 Slate 绘制元素；
- 海水、天空、特效、投射物、后处理、雾、Lumen 与世界中无关 Actor 不进入捕获视图。

## 3. 依赖红线与最低语义契约

### 3.1 严格单向依赖

必须长期保持：

```text
UI 小地图 -> 现有 gameplay 公共只读接口
gameplay -X-> UI 小地图
```

- 不允许为小地图修改 `RTSGameplay/`、`Units/`、`Iceberg/`、`Building/`、`Match/` 等 gameplay 代码；
- `UI/` 下仍只有 `RTSUIStateSubsystem.cpp` 可以 include gameplay 头，小地图控件、捕获 Actor、renderer 接口和纯视图类型都不得越界；
- facade 只把本帧 gameplay 事实投影成 UI 帧，不保存可参与玩法裁决的权威状态；
- 小地图点击只经 facade 调用现有相机公开入口，不让控件直接持有或识别 gameplay 类型。

违反后，gameplay 会开始为一种表现后端维护兼容逻辑，UI 将无法整体删除，且单位/地形实现变化会把小地图拖入同步修改。

### 3.2 “对 gameplay 无感”的准确边界

可以做到的是**对实现无感**，不能做到的是**对语义存在本身无感**。

首版只依赖两类已存在的公共事实：

1. 哪些 Actor 是当前登记的冰山；
2. 哪些单位和建筑是当前存活战斗目标，以及它们的世界位置、阵营和稳定目标 id。

因此，冰山内部从体素改成六边形、单位换模型/动画/表现池、建筑增加复杂逻辑，都不会影响小地图。真正的兼容边界是：新对象若不再登记为冰山，或不再发布为存活战斗目标，小地图就没有合法途径知道它存在。这不是小地图对实现的耦合，而是所有观察者都需要的最低发现契约。

潜水尤其需要区分：**位置在水下**不会让首版单位消失，小地图仍显示所有存活战斗目标。若未来玩法定义“潜水后敌方不可见”，必须由某个 gameplay 公共快照表达可见性/侦测语义；UI 不得靠模型高度、动画、Tag 名字或水面射线自行猜测，否则 UI 会制造第二套隐蔽规则。

### 3.3 既有公共契约的使用原则

- 地形发现使用冰山注册表的现有槽位与导航组件所有者，不遍历全世界猜 Actor 类型，也不读取体素场；
- 动态标记使用战斗子系统已经发布的存活单位与存活建筑连续快照，不读取 Mass fragment，不解析单位 Actor/模型；
- 选择态只从玩家控制器既有选择句柄在 facade 内投影为稳定战斗目标 id 集合，renderer 不认识 Provider；
- 主相机定位复用 CameraPawn 的既有公开焦点入口；若该入口的 Reset 语义将来改变，小地图跟随该公开契约，而不绕过相机自身约束。

## 4. 地形捕获决策

### 4.1 过滤机制

捕获采用正交 `SceneCapture2D` 的 ShowOnly 列表，而不是碰撞通道、Lighting Channel 或 Custom Stencil。

- 碰撞通道不参与可见性筛选；
- Lighting Channel 只决定灯光影响关系；
- Custom Stencil 是后处理标签，不能避免真实对象进入捕获视图；
- ShowOnly 从场景视图入口就把捕获限定为登记冰山，最符合“只画地形”的成本目标。

捕获后端由 UI 自己生成和销毁，既不要求关卡摆放专用 Actor，也不要求冰山添加“小地图组件”或设置特殊通道。这样新地图、程序化生成地图和 PIE 重开不会产生手工接线依赖。

### 4.2 捕获真实 Actor，而不是识别内部网格类型

ShowOnly 以注册表发现到的冰山 Actor 为边界，不查找名为 `VisualMesh` 的成员，也不判断它当前是 ProceduralMesh、StaticMesh 或未来的新表现组件。

这条决定是“冰山明天变成六边形也无需适配”的关键：捕获系统只问“这是登记的冰山吗”，由引擎渲染该 Actor 当下可见的 primitive。若未来一个登记冰山 Actor 上增加了不希望进入小地图的装饰性 primitive，应优先使用引擎通用的 SceneCapture 可见性标记在表现配置中排除；不要让小地图 include 新组件类型逐项识别。

### 4.3 固定世界边界与朝向

首版采用固定、北向上的世界矩形：世界 `+Y` 映射到小地图右侧，世界 `+X` 映射到小地图上方。地图中心和半范围属于 UI 表现配置，不从当前冰山包围盒动态推导。这个轴向已经成为地形、标记、相机框和点击反算的共同契约，后续不能只在其中一层做镜像来“修画面”。

否决动态自适应边界：冰山会漂移、碎裂或暂时离群，按对象包围盒自动缩放会让所有标记在屏幕上不断改变比例，玩家无法建立空间记忆，点击映射也会在拖动中变化。固定边界还能让 SceneCapture、UI 标记与输入共用一套稳定变换。

超出边界的地形由正交视图自然裁剪；动态标记和相机框在 UI 侧裁剪到内容区域。需要更大地图时调整 UI 配置，而不是改变 gameplay 世界。

### 4.4 颜色与光照

首版优先选择稳定、低成本的非光照捕获结果，而不追求主视角材质完全一致。小地图的任务是读轮廓与占位，不是复刻电影级表面。

捕获视图关闭阴影、动态光照依赖、后处理与高成本渲染特性，并用固定海色作为 RenderTarget 清屏。这样昼夜、雾、天空和主视角后处理不会让小地图忽明忽暗。若冰山最终材质在该捕获源下不可读，允许以后增加**纯表现侧**的 capture-only 代理或材质通路；不得因此读取并复制体素数据。

UE 5.8 的 BaseColor 捕获结果把有效颜色写在 RGB 中，但纹理 Alpha 不表达地形透明度。小地图必须把这张 RenderTarget 当作不透明颜色缓冲合成；普通图片控件按纹理 Alpha 混合会让捕获成功的地形完全不可见。该例外只属于小地图地形面，图标和其他 UI 纹理仍保留正常透明语义。

## 5. 动态标记与相机框

### 5.1 标记数据

facade 每帧把存活战斗目标投影成纯 UI 标记。renderer 只得到类别、世界二维位置、阵营、稳定 id 和是否选中等表现事实；不接触生命值 fragment、单位定义、动画实例、建筑 Actor 或命令状态机。

默认视觉规则保持简单且可辨认：单位使用小圆点，建筑使用更大的方形，己方/敌方/中立使用不同颜色，选中对象增加外圈或高亮。标记尺寸按屏幕像素固定，不随单位模型半径缩放，避免巨型模型把小地图盖满。

所有标记在单个 `NativePaint` 中批绘，不创建逐目标 UWidget，不为每个对象绑定委托，也不在场景里生成图标 Actor。

### 5.2 主相机可视范围

相机框不是用固定大小近似。facade 每帧从当前本地玩家视口四角反投影射线，与固定参考世界平面相交，得到一个纯二维四边形，再交给小地图绘制。

参考平面只服务概览提示，不声称精确贴合起伏冰山；用真实地形逐像素求交成本高且在海面/空洞处不连续。四边形能正确反映主相机旋转、俯仰、缩放和宽高比，已经满足经典 RTS 的方向与范围提示。

主相机接近平视时，射线可能在参考平面上得到远超固定地图边界的合法交点。此时保留真实投影点，并由小地图共同几何对线段做硬裁剪；不得逐点钳制到边界，因为那会把原本只穿过地图一角的线段扭曲成沿地图边缘延伸的假边。裁剪属于纯表现约束，不反向改变 facade 的投影语义。

投影失败或没有本地玩家视口时，只隐藏相机框，不影响地形和单位标记。

## 6. 刷新与性能模型

### 6.1 每帧路径

允许每帧发生的工作只有：

- SceneCapture 重画 ShowOnly 中的登记冰山；
- 顺序遍历现有存活战斗快照，生成连续的轻量标记数组；
- 计算四条视口反投影射线与平面的交点；
- Slate/UMG 批量绘制标记和相机框。

明确禁止进入每帧路径：全世界 Actor 遍历、体素/网格重建、逐单位组件查找、逐单位 Widget 生命周期、同步 GPU 回读、RenderTarget 转 CPU 纹理、材质或资产动态加载。

### 6.2 低频/按变化路径

冰山 ShowOnly 集合的发现频率与画面刷新频率分离。捕获可以每帧，但注册表槽位扫描只需按低频节奏或数量变化迹象重建；现有槽位允许出现空洞，因此不能仅以“数量相同”证明身份未变，低频全槽复核是可靠兜底。

RenderTarget 尺寸、地图边界和捕获配置只在初始化或配置变化时更新。首版不做运行时自动分辨率伸缩，避免在性能波动时引入额外资源重建与视觉跳变。

### 6.3 成本上限与降级顺序

ShowOnly 不等于免费：真实冰山的可见 mesh section 仍会为第二个场景视图提交并栅格化。若实测超预算，优化顺序必须保持职责不倒退：

1. 先压低 RenderTarget 分辨率和捕获特性；
2. 再把地形捕获降到隔帧或固定高频，标记与相机框仍每帧；
3. 再考虑由表现层维护低模 capture-only 代理；
4. 最后才评估专用 GPU 投影/缓存方案。

不得以“性能优化”为由改成捕获真实单位、让 UI 读取体素或要求 gameplay 主动推送小地图专用数据。那些做法会把暂时的帧耗问题变成长期架构耦合。

## 7. 输入与坐标映射

SceneCapture、动态标记和鼠标输入必须共享同一个世界矩形与同一轴向约定：世界 `+Y` 映射到递增的局部 X，世界 `+X` 映射到递减的局部 Y。这里既有世界轴到屏幕轴的交换，也有 UMG 局部 Y 向下带来的符号反转。Slate 直接采样 `UTextureRenderTarget2D`；在这套俯视捕获轴向下不需要对 Brush 再做垂直镜像。三处不得各写一套“看起来相近”的公式，否则最常见症状是地形、标记与点击之间出现镜像或错轴。

地形图像的实际内容矩形是地形、标记、相机框和输入的唯一局部坐标域，外框与装饰不得另造一块近似地图区域。Slate 的绘制几何和指针事件几何属于不同空间：绘制元素必须使用 Paint 空间，屏幕坐标反算必须使用 Tick 空间。不能用通用缓存几何同时服务两者，否则嵌入式 PIE、DPI 或 RenderTransform 会让叠加层被二次偏移，甚至被裁剪为完全不可见。

小地图继承现有交互面板基类，沿用统一的世界指针阻断：光标在小地图上时，边缘平移、框选、建造预览和背后世界点击都被阻断。左键按下后捕获鼠标，拖出面板仍继续按裁剪后的位置移动相机，抬起或捕获丢失时结束拖动。

点击产生的只是世界 XY 意图。facade 保留相机焦点当前 Z，并通过现有相机 Pawn 的公开入口完成定位；控件不直接操作 Pawn。该入口同时维护相机边界与 `ResetCamera(true)` 的初始焦点，这是既有相机契约的一部分，因此小地图点击会把新的位置作为后续“回到哪里”的焦点。

## 8. 生命周期、失败降级与资产边界

- 捕获 Actor 与 RenderTarget 都由小地图控件的运行时生命周期持有，控件重建、切图或世界退出时成对释放；关卡和 gameplay Actor 不保存它们的引用；
- facade 采用“最新 renderer 实例接管、旧实例只能注销自己”的既有规则，避免 WBP 重建时旧控件误清新控件；
- 没有 combat 子系统时显示地形但无标记；没有冰山注册表或尚未登记冰山时显示纯海色与其他可用标记；没有本地相机时隐藏相机框并拒绝定位请求；
- 原生 C++ 默认 WidgetTree 必须可独立运行。`WBP_RTSMinimap` 只接管布局与样式，蓝图不得写 Tick、事件图、属性绑定或直接读取 gameplay；
- 首版只增加 UI 资产，不要求修改关卡资产、冰山资产和 gameplay 蓝图。程序化地图与手摆地图继续走同一运行时捕获路径。

## 9. 被否决方案

### 9.1 全世界 SceneCapture

否决。它会重复提交真实单位骨骼网格、建筑、透明水面、特效、阴影和后处理；RenderTarget 分辨率变低只能降低像素成本，不能消除第二场景视图和 draw submission。

### 9.2 SceneCapture 捕获地形与真实单位

否决。单位模型、动画与材质复杂度会直接成为小地图成本，也使“单位换表现无需兼容”失效。UI 点能表达同一战术信息且成本稳定。

### 9.3 Custom Depth / Stencil 当渲染通道

否决。Stencil 适合后处理分类，不是对象剔除机制；它既不能自动排除背景，也不能免去对象真实网格的绘制成本。

### 9.4 UI 读取体素、导航格或程序化网格 section

否决。无论 CPU 投影多快，这都会让 UI 绑定当前地形实现，并复制“什么算表面”的第二份规则。地形改成六边形或换表现算法时必然同步修改小地图。

### 9.5 每个目标一个 UWidget

否决。它引入大量 UObject、布局、命中测试与生命周期管理，而标记本质上只是少量简单图元。经典 RTS 的数量增长路径应是连续数组与批绘，而不是控件树增长。

### 9.6 按当前对象包围盒自动缩放地图

否决。漂移、碎裂和离群对象会导致比例持续变化，破坏空间记忆、相机框尺度和拖动交互的一致性。

## 10. 后续扩展的准入条件

战争迷雾、潜水隐匿、雷达和伪装都属于**玩家可知性规则**，不是 UI 自行推断的视觉特效。只有 gameplay 已经提供与具体表现实现无关的公共可见性快照时，小地图才能消费它；否则宁可明确显示首版的全部存活目标，也不能从 Actor 类、模型位置或动画状态猜测。

地形代理、专用材质和 GPU 缓存属于表现后端替换，只要它们仍由 UI/表现层拥有、输入仍是登记冰山 Actor、gameplay 不反向依赖，就不改变本文架构。renderer 接口存在的目的正是让这些优化不扩散到 facade 和控件之外。
