# 编写长期技术文档

## 文档要解决什么

读者是下一个接手的 agent 或开发者。他们不了解当初的讨论，会多次打开这份文档。文档要让他们：

1. 几分钟内看懂这个系统做什么、不做什么、核心思路是什么；
2. 不再重新讨论已经定下的问题，不顺手做出破坏设计的修改，也不重踩已经踩过的坑；
3. 知道去哪段源码继续深入。

所以文档写的是**设计意图和理由**，只点出少数重点实现。它不是接口手册，也不是实现清单。代码是当前状态的唯一依据，文档只补代码表达不了的部分。

判断一条内容该不该写，问一句：**删掉它，读者会不会做出错误的决定？** 会才写。只是"少知道一件事"的，删掉。

## 第一步：收集材料

先收集，再动笔。

- **项目约定。** 读 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING` 等文件，确认文档目录、命名规则、语言和提交规范。没有约定时，沿用仓库里已有技术文档的风格。
- **工作中定下的事。** 最有价值的是代码里看不出来的决定：用户的要求和纠正、被否决的方案、调试时发现的坑。这些要连同原因写进文档。
- **源码。** 实现后写文档时，逐条核对结论与当前代码一致，记下真实的类名、函数名和关键数值。不要凭印象写。
- **其他来源。** 现有文档、提交信息、代码注释、测试都能帮助还原设计意图。相关系统已有技术文档的，引用文档名，不要重复它的内容。
- **缺少依据时问用户。** 某个设计的原因既不在上下文里，也不能从代码和历史中确认，就询问用户，或者明确标成待确认。不要编造理由。

更新已有文档时，先读全文，区分哪些结论仍然成立、哪些已被推翻、哪些是新增的，然后直接改写对应段落，使全文始终只描述当前设计。不要在末尾追加补丁章节。

## 第二步：确定要写的内容

该写：

- **目标与非目标。** 要做到什么，以及明确不做什么。非目标能防止后来者把范围外的需求塞进来。
- **核心方案。** 一句话的思路，加上为什么选它。
- **结构与职责。** 每层或每个模块只做什么、对应哪个类或目录、依赖方向是什么。
- **已敲定的结论和行为约定。** 每条都带原因。行为约定写清各种情况下系统怎么表现，包括空输入、失效、冲突、取消这类边界情况。
- **不变量和红线。** 必须长期保持的约束，例如"X 不得依赖 Y""只有 Z 能调用 W""A 必须在 B 之前"。每条写明**违反会发生什么**。
- **反直觉的坑。** 写**根因**而不是现象，再写正确做法。看起来能"顺手优化"、实际会出问题的地方，要明确提醒不要改。
- **被否决的方案。** 每个写一两句否决理由。下一个人最容易重新提出的，正是这些方案。
- **有含义的关键数值**，说明它为什么是这个值。
- **未实现的部分与扩展准入条件。** 哪些没做；以后要做时，前提是什么、不能破坏什么。

不写：

- 字段清单、类成员表、函数签名、参数全集。这些以源码为准。
- 操作步骤、命令、配置流程、验收与测试明细、构建结果、文件改动清单。
- 开发过程的叙述，比如"先做了 A，发现问题后改成 B"。只写结论 B，以及否决 A 的原因。
- 其他技术文档已经写过的设计。引用即可。
- 没有具体对象的泛泛原则，比如"保持良好的可扩展性"。

## 第三步：组织结构

参考下面的骨架。节名按系统调整，没内容的节删掉，复杂的机制可以拆成多节：

```markdown
# <系统名>

一两句：本文讲什么；相关系统见哪些文档。

## 目标与非目标

## 核心方案
一句话思路，以及为什么选它。

## 结构与依赖边界
各层职责、对应代码位置、依赖方向和红线。

## <核心机制或行为约定 1>、<2>……
每节由若干条结论组成：结论 + 原因 + 必要的关键实现点。

## 反直觉的坑（也可以并入对应机制）

## 被否决的方案

## 未实现的部分与扩展准入
```

## 写法要求

- **结论先行。** 每条以结论开头，加粗关键句，然后写原因。不要只写"必须这样做"而不解释。
- **红线配后果。** 写约束时写明违反会出现什么问题，读者才能判断例外情况。
- **用代码里的真实名字**（类、函数、字段），方便直接搜索源码。只点名关键的几个，不要逐个列举。
- **语气确定。** 已敲定的直接写成结论，不加"建议""可能"。还没定的写进未实现部分或标成待确认。
- **一个概念只用一个术语**，首次出现时说清它指什么。容易混淆的几种数据或概念要明确区分。
- **句子完整，指代清楚。** 精简不能简到读者需要猜。
- **少用图表。** 不用 Mermaid。数据流确实用文字讲不清时，可以画几行文本箭头图。输入到行为的对应关系适合用小表格，但表格不能用来列字段或参数。
- **语言跟随项目。**
- **控制篇幅。** 只保留会影响决定的内容。小系统一般在 100 行左右；大系统也应能在十分钟内读完，再长就按子系统拆成多份文档。压缩时先删实现细节，再合并重复的结论。

## 第四步：自检

交付前逐项检查：

- [ ] 实现后写的文档，每条结论都已和当前源码核对过。
- [ ] 工作中与用户敲定或否决的点都写进去了，并且带着原因。
- [ ] 没有编造的理由；依据不足的内容已经问过用户或标成待确认。
- [ ] 每条红线写了违反后果，每个坑写了根因和正确做法。
- [ ] 没有字段清单、命令块、验收步骤、测试明细和过程叙述。
- [ ] 没有重复其他文档已有的设计。
- [ ] 文件名、位置和语言符合项目约定，指向其他文档的链接有效。
- [ ] 读者只读本文，就能说出系统的核心思路。

## 收尾

- 只修改目标文档。其他文档里过时的描述、失效的链接，先告诉用户，由用户决定是否修改。
- 按项目规范决定是否提交以及如何写提交信息，未经允许不推送。
- 向用户简要说明：文档的结构、记录了哪些关键结论，以及篇幅（行数）。更新已有文档时，说明补了什么、删了什么。
