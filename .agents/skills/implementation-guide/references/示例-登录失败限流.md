# 实现指南：登录失败限流

> 【虚构示例】项目、文件、行号都是编的，只用来展示实现指南的粒度和写法，不要照抄内容。
> 一次性施工细则：验收合并后删除。长期设计写进 `docs/技术文档-认证.md`。
> 基线：分支 `main`，commit `a1b2c3d`。开工前工作区应当干净。
> 状态：用户已确认（2026-01-10）

## 1. 目标与范围

- 目标：同一账号短时间内多次输错密码后被临时锁定，锁定期间无法登录。
- 本期做：
  - 按账号的失败计数和锁定；
  - 接入密码登录入口；
  - 三项配置及启动校验。
- 本期不做：
  - 按 IP 限流（另开指南）；
  - 管理员手动解锁（用户暂不需要）；
  - OAuth 登录（不经过密码校验，不受影响）。

## 2. 必读

1. `src/auth/login.ts`：唯一的密码登录入口，接入点在这里。
2. `src/infra/kv.ts`：计数使用的存储客户端。
3. `docs/技术文档-认证.md`：现有的错误响应约定。

不用读：`src/auth/oauth/`、`src/web/`（与本功能无关）。

## 3. 已核对的事实

| 事实 | 出处 |
|---|---|
| 所有密码登录都经过 `handlePasswordLogin`；OAuth 不经过它 | `src/auth/login.ts:40` |
| 账号查找使用 `normalizeUsername` 规范化后的值（转小写、去首尾空格） | `src/auth/normalize.ts:12` |
| `kv.incrWithExpiry` 是原子自增，只在键新建时设置过期时间，之后的自增不刷新过期 | `src/infra/kv.ts:88`；存储官方文档的 INCR 与 EXPIRE 一节 |
| 现有登录失败统一返回 `INVALID_CREDENTIALS`，不区分账号是否存在 | `src/auth/errors.ts:5` |

请查证（结论写进报告）：

- 测试用的内存版 KV（`test/fakes/kv.ts`）是否实现了过期。这会影响自动化测试用假时钟还是真实等待。没有实现就报告，不要自己补实现。

## 4. 架构与归属

| 新增 | 位置 | 职责（一句话） |
|---|---|---|
| 登录限流模块 | `src/auth/throttle/` | 按账号记录失败次数，并判断当前是否锁定 |
| 错误码 `LOGIN_LOCKED` | `src/auth/errors.ts` | 锁定期间的响应，携带剩余秒数 |

- 依赖方向：`login.ts` 调用限流模块，限流模块只依赖 KV 客户端，不知道 HTTP 的存在。
- 不新增中间件：中间件拿不到密码校验的结果，没法只统计失败。
- 不新增数据库表：计数是短期数据，用 KV 的过期时间自然清理。
- 公共接口（供 `login.ts` 调用）：
  - 检查账号：返回"允许"，或"已锁定 + 剩余秒数"；
  - 记录一次失败；
  - 记录一次成功。

## 5. 不变量与禁区

1. 锁定检查必须在密码校验之前执行。违反后果：锁定期间仍会校验密码，正确密码会登录成功，或者产生可以测量的响应时间差。
2. 不修改 `normalizeUsername`。原因：其他模块依赖它，改了会让已有账号查不到。
3. 日志不得包含明文账号名或密码，账号只记哈希。违反后果：日志泄露凭据。

## 6. 决策表

| # | 场景 | 行为 | 来源 | 日志 |
|---|---|---|---|---|
| D1 | 计数按什么区分 | 按 `normalizeUsername` 的结果计数 | 设计推导：与账号查找使用同一个键，否则改变大小写就能绕过计数 | 无 |
| D2 | 窗口怎么计时 | 窗口从该账号窗口内的第一次失败开始计，到期后计数清零；之后的失败不顺延窗口 | 用户确认："10 分钟内错 5 次就算" | 无 |
| D3 | 达到阈值的那次失败 | 仍返回 `INVALID_CREDENTIALS`；从下一次请求开始返回 `LOGIN_LOCKED` | 设计推导：这次的密码已经校验过，结果就是密码错误 | 进入锁定时 Warning |
| D4 | 锁定期间输入正确密码 | 拒绝，返回 `LOGIN_LOCKED`，不校验密码 | 用户确认："锁定期间就算密码对了也不让登" | 无 |
| D5 | 锁定期间的请求 | 不计入失败，不延长锁定 | 设计推导：否则攻击者能让账号一直处于锁定 | 无 |
| D6 | 账号不存在 | 和存在的账号一样计数、锁定，响应完全一致 | 用户确认："不要告诉对方账号存不存在" | 无 |
| D7 | 登录成功 | 清零该账号的失败计数 | 设计推导：正常用户偶尔输错一次，不应一直带着计数 | 无 |
| D8 | 同一账号的失败请求同时到达 | 每次都计数，使用原子自增，不先读后写 | 设计推导：先读后写会让并发猜测少计数 | 无 |
| D9 | KV 不可用 | 拒绝登录，返回服务暂不可用 | 用户确认："限流挂了就别让登，别偷偷放行" | Error |
| D10 | 配置缺失或非法 | 服务启动失败并报错，不使用默认值 | 设计推导：使用默认值属于兜底，用户没有同意 | Error |

需要用户确认的分支：D9 选择拒绝登录而不是放行（用户已同意）。本期不新增任何兜底分支。

边界核对清单中不处理的项：

- 账号在锁定期间被删除：不处理，计数随过期自然清除。
- 服务重启：不需要处理。计数在 KV 里，重启不清零，这是预期行为。

## 7. 数据与配置

| 参数 | 含义 | 初值 | 合法范围 | 非法时 |
|---|---|---|---|---|
| `LOGIN_MAX_FAILURES` | 窗口内触发锁定的失败次数 | 5 | 整数，≥ 1 | 启动失败，按 D10 |
| `LOGIN_FAILURE_WINDOW_SECONDS` | 失败计数窗口 | 600 | 整数，≥ 1 | 启动失败，按 D10 |
| `LOGIN_LOCK_SECONDS` | 锁定时长 | 900 | 整数，≥ 1 | 启动失败，按 D10 |

## 8. 验收场景

- 场景：本地启动服务，在登录页登录。
- 初始布置：已存在账号 `demo`，密码已知。为了方便手动验收，本地把 `LOGIN_LOCK_SECONDS` 改成 60，`LOGIN_FAILURE_WINDOW_SECONDS` 改成 120。
- 步骤与期望：
  1. 用错误密码登录 5 次 → 每次都提示"账号或密码错误"；第 5 次时服务日志出现一条 Warning"账号已锁定"，只带账号哈希。
  2. 第 6 次用正确密码登录 → 提示"尝试次数过多，请稍后再试"。
  3. 等待 60 秒后，用正确密码登录 → 登录成功。
  4. 对不存在的账号 `nobody` 重复步骤 1、2 → 提示和 `demo` 完全一致。
  5. 停掉本地 KV 后登录 → 提示服务暂不可用，日志出现 Error。
- 必须成立的数值关系：步骤 1 的 5 次失败要在 120 秒内完成，否则窗口到期、计数清零，不会锁定。
- 自动化测试要证明：
  - 窗口内第 5 次失败后锁定；窗口到期后失败重新计数（D2、D3）；
  - 锁定期间正确密码被拒绝，且锁定时长不变（D4、D5）；
  - 不存在的账号与存在的账号响应一致（D6）；
  - 10 个并发失败请求计数为 10（D8）；
  - KV 不可用时拒绝登录（D9）；配置非法时启动失败（D10）。
