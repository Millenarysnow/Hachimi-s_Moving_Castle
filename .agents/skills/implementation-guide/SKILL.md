# 编写实现指南

## 指南要解决什么

读者是 worker：它没有参与需求讨论，按指南一次性完成实现，然后提交审查。指南要让它：

1. 不需要自己做任何"选错会返工"的行为决策；
2. 不需要重新查证 orchestrator 已经查过的事实；
3. 知道交付到什么程度算完成，以及用户会怎么验收。

指南是**一次性**的：功能验收合并后，删除或归档。需要长期保留的设计理由，由 worker 收尾时按 `tech-design-doc` skill 写进技术文档。

与技术文档的区别：技术文档写"为什么这样设计"，给以后反复查阅的人看；实现指南写"这次要做成什么样、边界怎么处理、怎样算做完"，只给这次的 worker 看。两者有重叠时，指南引用技术文档，不复述。

## 粒度原则

**判据：一项决策如果 worker 选错，会不会导致返工、验收失败或静默出错？会，就由指南定死；不会，留给 worker。**

指南定死的：

- 行为语义与边界情况（见「边界核对清单」）。
- 对外可见的类型、接口、数据和资源：归属、命名、所在目录。
- 依赖方向，以及不许碰的文件和行为。
- 数据与配置的含义、初值、合法范围；非法值怎么处理。
- 验收场景，以及场景成立需要的数值关系。
- 已核对的事实。

留给 worker 的：

- 函数怎么拆、私有辅助函数、内部变量名。
- 数据结构和循环写法。
- 测试用例的具体写法（指南只写测试要证明什么）。
- 注释措辞和日志文案（除非验收要靠某条日志判断）。

**不写代码。** 指南里不出现能直接复制进源文件的片段，也不给私有函数列签名。需要说明流程时，只写因果顺序（"先 A 后 B，因为……"），不写逐行步骤。跨模块的公共接口例外：可以给签名和语义，不给函数体。

**两个自检：**

- **太薄：** worker 读完还得自己决定"没有目标怎么办""状态归谁""出错后状态留不留"，说明决策表漏了。把核心判断留成 `<待定>` 一类占位，是最常见的太薄。
- **太厚：** 指南里有可复制的代码块，或者每个私有函数都有签名，说明 orchestrator 在替 worker 实现，省钱的目的就落空了。逐帧、逐行的执行流程也算太厚。

## 第一步：查证与收集

先查证，再动笔。

- **项目约定。** 读项目的规则文件和文档约定，确认临时文档的命名和位置、提交规范，以及需要用户确认才能加的分支（例如兜底、默认值、静默过滤）。
- **用户原话。** 收集用户对本功能说过的话，包括要求、纠正和否决。写进决策表时原样引用，不改写。改写最容易丢语义，例如"触发后就执行一次"被改写成"按速率依次执行"，空闲时的第一次执行就被推迟了一个间隔。
- **相关代码和文档。** 只读与本功能相关的部分，确认要接入的位置、现有的约束和测试。
- **外部行为。** 指南依赖的框架、引擎或库的行为，看源码或官方文档确认，记下出处。凭印象写下的错误前提，worker 会照着做错。
- **查不到的。** 能由 worker 在开工时查清、且查证结果不影响架构的，标成「请查证」交给 worker；会影响架构的，自己查清或问用户。不要编造。

## 第二步：选完整指南或轻量指南

同时满足以下三条，用轻量指南（[references/模板-轻量指南.md](references/模板-轻量指南.md)），否则用完整指南（[references/模板-完整指南.md](references/模板-完整指南.md)）：

1. 不新增对外可见的类型、接口或资源；
2. 不改数据结构、配置格式或存储格式；
3. 预计改动在约 200 行以内（经验值，可按项目调整）。

轻量指南只保留目标与范围、已核对的事实、决策表、验收场景，同样要经过用户确认。

## 第三步：写

按模板的节顺序写。各节要点：

- **目标与范围：** 一句话目标；本期做什么、明确不做什么；基线分支和 commit。"不做什么"能防止 worker 把范围外的需求带进来。
- **必读：** 按顺序列出要读的文件或文档，并写明哪些不用读，避免 worker 为了"建立全貌"遍历仓库。
- **已核对的事实：** 每条附出处（文件和行号，或文档链接）。worker 直接采用，不重查。「请查证」的项单独列出，写明查证结果会影响哪条决策。
- **架构与归属：** 新增哪些类型或模块、放在哪个目录、各自一句话职责、依赖方向；明确不新增什么，以及为什么。
- **不变量与禁区：** 这期不许改的文件或行为，违反会静默出错的规则。每条写明违反的后果，worker 才能判断例外情况。
- **决策表：** 每行是"场景 | 行为 | 来源 | 日志级别"。来源只有两种：用户确认（附原话或确认时间），或设计推导（附一句理由）。项目规则要求用户确认的分支逐条列出，并标明用户是否已同意；没同意过的先问用户，不要写进指南等 worker 去实现。
- **数据与配置：** 字段或参数的含义、初值、合法范围，非法值怎么处理。初值属于需求，必须给出，不留给 worker。
- **验收场景：** 用户实际会打开什么、做什么、看到什么。写明初始布置、操作步骤、期望现象，以及场景成立需要的数值关系（例如"测试目标必须始终在作用范围内"）。自动化测试只列"要证明什么"。
- **分期与提交点：** 需要分期时，写明每期的边界、是否改变现有行为、对应几个提交。每期都要能单独构建。
- **交付：** 引用《Worker 工作规程》的完成报告条目；只补本功能特有的条目。

## 边界核对清单

对每个新增行为逐项过一遍。每一项要么写进决策表，要么写明"不处理，原因是……"：

- 初始状态和空闲状态下第一次触发怎么表现。
- 短时间内或同一帧、同一请求周期内多次触发：合并、排队、丢弃，还是逐个处理。
- 速率、冷却、窗口这类时间语义：从什么时候开始计时，什么事件会重置它。
- 输入为空、没有目标、目标不存在。
- 目标在处理途中失效、被销毁或被替换。
- 配置或资源缺失、格式非法、数值越界。
- 并发和重入：同时到达的请求或回调会不会读到中间状态。
- 出错后：状态保留还是回滚，下一次触发重试还是放弃。
- 对象销毁、关闭、重启时，未完成的工作怎么处理。

## 文件名与位置

- 按项目的临时文档约定命名和放置，例如 `<文档目录>/Temp-实现指南-<功能名>.md`。项目没有约定时问用户。
- 指南必须放在 worker 能读到的地方。worker 在独立工作区从基线 commit 开工时，指南要么已经提交进基线，要么用 worker 可访问的绝对路径给出。按项目规则选。

## 第四步：自检

交付前逐项检查：

- [ ] 用户原话逐句对照过决策表，没有被改写。
- [ ] 边界核对清单的每一项都有着落：写进决策表，或写明不处理的原因。
- [ ] 需要用户确认的分支都已确认，并标了来源。
- [ ] 每条事实都有出处；「请查证」的项写明了会影响哪条决策。
- [ ] 每个参数都有初值和合法范围。
- [ ] 验收场景写明了操作和期望现象，所需的数值关系成立。
- [ ] 没有可复制的代码块，没有私有函数签名，没有逐行流程。
- [ ] worker 只读本指南和必读清单，就能开工，不需要再问行为问题。

## 收尾

- 把指南交给用户确认，并单独指出：决策表里来源为"设计推导"的条目，以及边界核对清单里写了"不处理"的项。这两类最需要用户过目。
- 用户的修改直接改进指南。不在派发消息里另附补充说明。
- 用户确认后再派发。
